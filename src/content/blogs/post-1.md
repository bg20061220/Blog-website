I spent two weeks building an AI-powered component builder — a landing page generator you control through natural language prompts. The idea felt sharp. Halfway through, I realized I had built a worse version of ChatGPT with a canvas attached to it.

I kept going anyway, adding features, hoping the project would eventually justify itself. It didn't. I shelved it.

This post isn't about the product. It's about what building it properly — from scratch, no shortcuts, no agent frameworks — taught me about how AI agents actually work.

---

## What I Built

The system let users describe UI components in plain text and an LLM would translate that into structured JSON, which then rendered as real React components on a canvas. You could say "add a pricing section with three cards" or "change the button color to blue" and the agent would figure out which tool to call and with what parameters.

Under the hood: Groq's Llama 3.3 70B as the reasoning model, a custom tool registry of 8 functions, a Zustand store managing component state, and a WebSocket layer handling real-time updates. No agent framework. The loop was written by hand.

## How an AI Agent Actually Works

Before building this, I'd read plenty of explanations of agents. None of them clicked the way actually building one did.

### The Agent Loop

An agent is a loop. That's it. Inject context, call the LLM, parse output, execute a function, update state, repeat. The "intelligence" isn't magic — it comes down to how clearly your system prompt explains what tools exist and when to use them.

My loop looked like this:

```
user input
  → inject current canvas state (all component IDs + hierarchy)
  → LLM outputs: { tool: "modify_component", params: { ... } }
  → parse JSON
  → execute the matching function
  → update store → re-render UI
  → next turn
```

When the prompt was clear, the agent picked the right tool with the right parameters almost every time. When it was vague, it guessed wrong — consistently.

### Tools Are Just Functions

An AI tool is literally just a function with a name, a description, and a parameter schema. The LLM doesn't run it — you do. The model decides which one to call and what to pass in. You execute it.

My eight tools: `create_component`, `modify_component`, `delete_component`, `add_child`, `reorder_child`, `clear_canvas`, `create_form`, `create_section`. Each one was a plain JavaScript function. The "AI" part was just the LLM deciding which one to invoke.

### Context Is Everything

The agent kept failing to target nested components — a button inside a form, a card inside a grid. It wasn't a model problem. The model simply couldn't see those elements.

The fix was a `flattenComponents()` function that walked the entire component tree and exposed every element — including children — with a reference to their parent. Once the agent had the full picture, targeting worked correctly.

Garbage context produces garbage decisions. Obvious in retrospect, easy to miss while building.

### Memory Is Injected History

LLMs are stateless. They remember nothing between API calls. "Memory" in an agent is just conversation history you include in every request.

I was storing full component JSON blobs per turn and burning tokens fast. The fix: strip history down to `{ tool, message }` per turn, cap at 10 turns. The agent could still understand references like "that button" or "the card we just added" without carrying the full state in every prompt.

## Technical Bugs Worth Knowing About

A few specific problems that cost real time and aren't obvious from the outside.

### Structured Tool Calling Was Unreliable

Groq models produced malformed outputs when I used the framework's built-in tool calling. The more debuggable solution: prompt the model to output a raw JSON blob inside its text response, then parse it manually with a custom `extractJSON()` function. More code, but when it broke I could see exactly why.

One edge case that bit me: the brace-depth counter I used to find JSON boundaries would fire on `{}` inside string values — CSS fragments, mostly — causing false "Unclosed JSON" errors. The real fix was tracking `inString` state and skipping characters inside quoted strings entirely.

### State Mutation Shape Mismatch

The agent sent changes shaped like `{ style: { color: "blue" } }` at the props level. My store was merging with `{ ...component, ...changes }`, which put `style` at the root of the component object. But the renderer read from `props.style`. Changes had zero visual effect and no error was thrown.

Fix: merge changes into `props` specifically, with a deep merge for nested objects.

```js
// Wrong
store.updateComponent(id, { ...component, ...changes });

// Right
store.updateComponent(id, {
  ...component,
  props: deepMerge(component.props, changes),
});
```

### Stale Closures in Socket Listeners

`socket.on("tool_call", callback)` captured the callback at mount and never updated it. After any re-render, the socket was calling a stale version of the function. `clear_canvas` appeared to do nothing until page refresh.

Fix: store all callbacks in refs, update the refs on every render, have listeners call `ref.current()` instead of the captured value directly.

### The Two-Sided Fix Problem

The agent couldn't modify nested components until I exposed their IDs in context. But exposing the IDs wasn't enough — the Zustand store also needed a recursive `applyUpdate()` that could traverse the tree and find the right target. Fixing only one side did nothing. Both the context and the store had to support the same operations simultaneously.

This pattern shows up a lot in agent systems: the model's view of the world and your state layer's capabilities have to stay in sync.

## What Actually Went Wrong With the Idea

The technical execution was fine. The problem was that the core idea — "describe a UI component with text and watch it appear" — is already what any general-purpose LLM does. I had built a more constrained, less capable version of something that already existed for free.

At some point the learning value dried up and I was just decorating a dead end. I kept adding features trying to find an angle that worked. I didn't find one.

The harder lesson: building to learn and building to avoid admitting a bad idea feel identical in the moment. The output looks the same. The git commits look the same. The difference only shows up later.

---

## Worth It Anyway

I don't regret the two weeks. Writing the agent loop by hand, designing the tool schemas, debugging why the model made wrong decisions — that's the kind of thing that doesn't come from reading blog posts about agents. It comes from breaking them.

If you're trying to understand how agents work, build something dumb. It doesn't need to ship. It just needs to be real enough to fail in interesting ways.
